# beFruitbe Knowledge Base

[English version](README.md)

## Описание

В рамках проекта beFruitbe AI Content Pipeline я самостоятельно спроектировал и собрал Knowledge Base, которая должна была стать источником проверенного контекста для AI-агентов.

Задача состояла не просто в том, чтобы загрузить несколько документов в LLM.

Необходимо было построить структуру, которая позволяла бы AI-системе понимать:

- что представляет собой бренд;
- что такое СОКОчай как продуктовая категория;
- какие продукты реально существуют;
- какие факты о них подтверждены;
- как говорит бренд;
- какие визуальные материалы разрешено использовать;
- какие утверждения допустимы;
- какие данные требуют дополнительного подтверждения.

Knowledge Base использовалась в Custom GPT Script & Prompt Agent и проектировалась как центральный источник контекста для остальных компонентов системы.

---

## Моя роль

Структуру Knowledge Base я разработал самостоятельно.

Работа включала:

1. определение того, какие данные потребуются AI-системе;
2. создание подробного чек-листа материалов для компании;
3. определение требований к качеству и метаданным файлов;
4. создание списка вопросов владельцам и другим участникам команды;
5. получение материалов от компании;
6. проведение интервью с двумя владельцами;
7. расшифровку интервью;
8. структурирование полученной информации;
9. создание отдельных разделов Knowledge Base;
10. подготовку таблиц SKU и product data;
11. создание системы claims и ограничений;
12. подготовку Tone of Voice и content rules;
13. подготовку требований к фото, видео и другим assets;
14. загрузку подготовленных материалов в Custom GPT;
15. тестирование Knowledge Base на реальных сценариях.

Каждое интервью с владельцами длилось примерно 1,5 часа.

---

## Зачем потребовалась Knowledge Base

Без структурированного контекста LLM могла:

- придумывать свойства продукта;
- смешивать характеристики разных SKU;
- использовать неподходящий Tone of Voice;
- придумывать ингредиенты;
- создавать неподтверждённые claims;
- неправильно объяснять продукт;
- предлагать визуальные решения, не соответствующие реальной упаковке.

Поэтому принцип проекта был:

```text
User Prompt
     +
Verified Brand Knowledge
     ↓
AI Agent
     ↓
Brand-aware Output
```

а не:

```text
User Prompt
     ↓
Generic LLM
     ↓
Creative Guess
```

Архитектура Knowledge Base включала несколько типов данных.

### Brand & Category

- определение категории;

### Product & Technology

- правила описания процесса;

- вкус;
- состав;
- характеристики;
- упаковка;

### Tone of Voice & Messaging

- стиль коммуникации;
- допустимые формулировки;
- нежелательные формулировки;
- примеры;
- правила диалогов;
- CTA.

### Visual & Production Rules

- правила использования упаковки;
- реальные фотографии продукта;
- требования к изображениям;
- видео;
- генеративному AI;
- continuity;
- монтажу.

### Media Library

- фотографии;
- видео;
- аудио;
- графика;
- реальные product assets.

### Rights

- права на использование логотипа;
- упаковки;

### Content Registry

История созданного контента и его характеристик.

### Analytics

Будущие подтверждённые выводы Content Analytics Agent.

## SKU Master и Google Sheets

Google Sheets использовались для структурированных данных.

Одна из задач состояла в том, чтобы AI мог работать не с неструктурированным набором документов, а с конкретными сущностями продукта.

Упрощённо:

```text
SKU
 ├── Product Name
 ├── Flavour
 ├── Composition
 ├── Packaging
 ├── Product Facts
 ├── Claims
 ├── Status
 └── Related Assets
```

Это позволяло в дальнейшем связывать:

```text
User Request
     ↓
Specific SKU
     ↓
Verified Facts
     ↓
Approved Assets
     ↓
Script
```

## Claims Matrix

Отдельная часть базы предназначалась для контроля продуктовых утверждений.

AI-система не должна была считать любую найденную формулировку разрешённой.

У утверждений мог быть различный статус:

```text
APPROVED
DRAFT
CONFIRMATION REQUIRED
NOT ALLOWED
```

Если необходимый факт не был подтверждён, сценарист должен был остановиться на этапе публикации или явно обозначить необходимость проверки.

## Media Library

Для будущего AI Content Pipeline было важно хранить не только тексты.

Knowledge Base проектировалась также как система реальных медиа-источников:

```text
Photos
Video
Audio
Graphics
Packaging
Product
```

Особое значение имели реальные фотографии упаковки.

Во время тестов генеративных моделей стало понятно, что AI может:

- искажать логотип;
- менять надписи;
- создавать нечитаемый текст;
- изменять дизайн упаковки.

Поэтому реальный asset имел приоритет перед генерацией критически важных брендовых элементов.

## Метаданные

Для материалов проектировалась система метаданных.

Для документа было важно понимать:

```text
что это;
какая версия;
к какому продукту относится;
кто подтвердил;
какой статус;
можно ли использовать в Knowledge;
можно ли публиковать;
какие есть ограничения.
```

Упрощённая карточка:

```text
Name
Version
Date
Owner
Status
Scope
Usage Permission
Publication Permission
Notes
```

Это позволяло отделять:

```text
актуальное
от
архивного

подтверждённое
от
чернового

публичное
от
конфиденциального
```

Для сборки Knowledge Base использовалась приоритизация.

### P0 — блокирует запуск

- определение продукта;
- пилотный SKU;

- упаковка;

### P1 — производство

- product photos;

### P2 — бренд

- Tone of Voice;

- примеры коммуникации.

- дополнительные SKU;
- производство;

Такой подход позволял не ждать полной готовности огромной базы перед запуском первых тестов.

## MVP для первого ролика

Кроме полной архитектуры Knowledge Base я подготовил отдельный минимальный набор данных для запуска первого ролика.

Идея:

> собрать только те данные, отсутствие которых реально блокирует производство.

В MVP входили:

- задача ролика;
- критерий приёмки;
- конкретный продукт;
- человек, утверждающий результат;
- актуальные фотографии упаковки;
- оригинальный макет упаковки;
- состав и инструкция;
- разрешённые и запрещённые claims;
- описание вкуса;
- Tone of Voice;
- персонажи;
- логотип;
- фирменные элементы;
- параметры озвучки;
- разрешение на использование материалов;
- разрешение на загрузку материалов в AI-сервисы.

Это позволяло начинать production до завершения полной Knowledge Base.

## Проверка достоверности

Основными источниками истины были:

1. информация владельцев;
2. официальные материалы компании;
3. подтверждённые продуктовые данные;
4. утверждённые материалы маркетинга.

При конфликте данных я запрашивал подтверждение у владельца и директора по маркетингу.

AI не должен был самостоятельно выбирать, какая из конфликтующих версий «скорее правильная».

---

## Что оказалось наиболее полезным

Для Script & Prompt Agent наиболее полезными частями Knowledge Base оказались:

- Tone of Voice;
- SKU data;
- история и контекст бренда;
- продуктовые ограничения;
- правила достоверности.

Они позволяли агенту сохранять творческую свободу в сценариях, не выходя за пределы подтверждённой информации о продукте.

## Конфиденциальность

Полная Knowledge Base не публикуется в этом репозитории.

Она содержит внутреннюю и конфиденциальную информацию компании.

В публичном GitHub представлены только:

- архитектура;
- структура;
- принцип работы;
- обезличенные примеры;
- публичные product assets, если их использование разрешено.

Оригинальные:

- интервью;
- SKU tables;
- Claims Matrix;
- внутренние документы;
- закрытые данные;
- private assets

остаются вне публичного репозитория.
