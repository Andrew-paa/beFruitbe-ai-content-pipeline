# beFruitbe Knowledge Base

[Русская версия](README_RU.md)

## Overview

As part of the beFruitbe AI Content Pipeline, I independently designed and assembled a Knowledge Base intended to provide verified brand context to AI agents.

The goal was not simply to upload several documents into an LLM.

The system needed structured information allowing AI components to understand:

- what the brand represents;
- what the product category is;
- which products actually exist;
- which product facts are verified;
- how the brand communicates;
- which visual assets may be used;
- which product claims are allowed;
- which information requires additional verification.

The Knowledge Base became the primary contextual layer for the Custom GPT Script & Prompt Agent and was intended to support other components of the future pipeline.

## Why a Knowledge Base Was Required

Without structured context, an LLM could:

- invent product properties;
- mix information between different SKUs;
- use an incorrect Tone of Voice;
- invent ingredients;
- produce unsupported claims;
- explain the product incorrectly;
- suggest visuals inconsistent with real packaging.

The intended principle was:

```text
User Prompt
     +
Verified Brand Knowledge
     ↓
AI Agent
     ↓
Brand-aware Output
```

rather than:

```text
User Prompt
     ↓
Generic LLM
     ↓
Creative Guess
```

## Structured SKU Data

Google Sheets were used for structured product information.

The purpose was to allow AI components to work with identifiable product entities rather than an unstructured collection of documents.

Simplified structure:

```text
SKU
 ├── Product Name
 ├── Flavour
 ├── Composition
 ├── Packaging
 ├── Product Facts
 ├── Claims
 ├── Status
 └── Related Assets
```

The intended retrieval flow:

```text
User Request
     ↓
Specific SKU
     ↓
Verified Facts
     ↓
Approved Assets
     ↓
Script
```

## Claims Matrix

Product claims were managed separately.

A statement found somewhere in the project materials was not automatically treated as safe for publication.

Possible states included:

```text
APPROVED
DRAFT
CONFIRMATION REQUIRED
NOT ALLOWED
```

If a required fact was not verified, the Script Agent could continue developing the concept while explicitly blocking publication until human confirmation.

---

## Media Library

The Knowledge Base was designed to contain more than text.

The future AI pipeline also required verified media assets:

```text
Photos
Video
Audio
Graphics
Packaging
Product
```

Real packaging photography was particularly important.

During generative-video experiments, AI models could:

- distort logos;
- modify text;
- produce unreadable labels;
- change packaging design.

For critical brand elements, verified real assets therefore had priority over AI-generated substitutes.

## Metadata

The system was designed to preserve metadata for project materials.

For each asset or document, the system needed to understand:

```text
What is it?
Which version?
Which product?
Who verified it?
What is its status?
Can AI use it?
Can it be published?
What restrictions apply?
```

Simplified document metadata:

```text
Name
Version
Date
Owner
Status
Scope
Usage Permission
Publication Permission
Notes
```

This helped separate:

```text
current vs archived
verified vs draft
public vs confidential
```

## MVP Dataset for the First Video

In addition to the full Knowledge Base architecture, I created a reduced MVP data package for the first video.

The principle was:

The MVP included:

- video objective;
- acceptance criteria;
- specific product;
- final approver;
- current packaging photos;
- original packaging artwork;
- composition and preparation instructions;
- approved and prohibited claims;
- flavour description;
- Tone of Voice;
- characters;
- logo and brand elements;
- voice requirements;
- usage permissions;
- permission to upload assets to AI services.

This allowed video production to begin before the entire long-term Knowledge Base was complete.
